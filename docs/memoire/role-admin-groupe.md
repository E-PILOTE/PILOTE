`admin_groupe` est **online (Supabase direct)**, comme super_admin — PAS PowerSync offline. C'est un ministère ou un promoteur qui gère plusieurs écoles : il configure ses écoles, voit les détails, gère bénéfices/dépenses/personnels, KPIs temps réel.

**Why:** clarification explicite de l'utilisateur (session 2026-05-31). Il n'**utilise** pas les pages des modules (ça c'est le personnel, offline-first) → pas besoin du offline-first ; les modules sont le catalogue plateforme (créé par super_admin) consommé par le personnel.

**MàJ 2026-06-04 — admin_groupe PILOTE bien les modules** (l'ancienne note « ne touche pas aux modules » est nuancée) : sidebar « Modules du groupe » dynamique (`adminNavModulesProvider`, `app_shell.dart:176-192`) + écran `AdminModuleScreen` route `/admin/modules/:slug`. Il **attribue** les modules aux profils d'accès via `profile_permissions`, mais n'**ouvre jamais** une page fonctionnelle (inscrire un élève, etc.). Hiérarchie complète des modules → voir [[modules-acces-hierarchie]].

**MàJ 2026-06-04 (soir) — `AdminModuleScreen` = éditeur de GOUVERNANCE d'accès (pas un tableau de bord).** Itéré en 2 temps : (a) plainte « je click sur un module et j'ai rien » → 1er jet = cockpit lecture-riche (KPI + déploiement par école + volume métier) ; (b) l'utilisateur l'a jugé **redondant** (ces KPI sont déjà au Dashboard/Rapports) et **sur-chargé** (l'admin_groupe ne fait qu'UNE chose avec un module : décider QUI peut l'utiliser). Design final = bonne pratique M365/Google Workspace/Okta : **par-module = gouvernance d'accès UNIQUEMENT ; usage/adoption = analytics centralisés (Dashboard/Rapports), jamais redupliqués par module.** L'écran liste les profils d'accès du groupe avec, pour CE module, un **sélecteur de niveau inline** (Aucun / Lecture seule / Contribution / Gestion complète) + nb membres impactés ; tag « réglage fin » si les perms ne matchent aucun preset (combinaison définie via la matrice). Header = badge `autorisés/total` + 1 ligne ; pied = renvoi vers `/admin/profils` pour le réglage fin (9 actions + périmètre).

**Écriture inline SÛRE (motif à réutiliser partout où on touche `profile_permissions`)** : le RPC `set_profile_permissions` fait `DELETE puis re-INSERT` de TOUTES les permissions du profil (replace complet + clamp hiérarchique + audit). Donc pour changer le niveau d'UN module sans effacer les autres : charger la map COMPLÈTE du profil (`accessProfilePermsProvider(profileId)` → `Map<moduleId, PermRow>`), modifier/retirer SEULEMENT la ligne de ce module, puis renvoyer l'ensemble via `AdminAccessService.savePermissions`. Niveau→booléens (presets identiques à la matrice → rows identiques) : Lecture=read ; Contribution=read+create+update ; Gestion=les 9 `can_*`=true ; Aucun=on RETIRE la ligne (pas de row = pas d'accès, cohérent avec le comptage `moduleCount`). `ModuleProfileAccess.perm` réutilise le `PermRow` de `admin_access_provider.dart`. Provider `admin_module_provider.dart` réécrit **lean** (module + plan + profils + perms du module ; supprimé : schools/staffBySchool/domain KPIs/`_domainSources`). analyze 0 issue, hot reload ✓. Principe transverse → voir [[design-gouvernance-anti-redondance]].
